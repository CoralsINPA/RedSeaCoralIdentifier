## The segmentation check (notebook 01, step 2)

`run_segmentation_check(cfg, n=5, photos_dir="data_50", prefix="segcheck_")`:

1. `check_config` copies the active config with `paths.run_prefix = "segcheck_"` and `images_dir = "data_50"`. It refuses a config whose JSON folder is the active one.
2. `choose_check_photos` takes `n` photos that have a JSON in the active run (seeded shuffle; a portrait photo is swapped in when none was drawn and the first `max(4n, 20)` candidates have one).
3. `run_segmentation` segments them into `results_all/segcheck_iou60_sta55_pts32/json/`. A photo already segmented there is not segmented again (nothing is overwritten); a new `prefix` redoes the check.
4. `mask_compare.compare_segmentations` reads both folders. Per photo: the frame, the mask count, and the masks matched **one to one by IoU** (greedy, best first; a saved mask is "found again" at IoU >= 0.9), the mean best IoU, each for all masks and for the large ones (area >= `filters.min_area`, 25,000 px, the ones that survive the filters).
5. Verdict (limits are guesses; revise after the first real run). **FAIL:** a frame differs, a photo could not be segmented, fewer than 50% of the large saved masks are found again, or the mask count is under half or over twice the saved one. **WARN:** under 90% of the large masks, under 80% of all masks, or the count outside 0.8 to 1.25 times. **PASS:** otherwise.
6. `write_segmentation_check` saves `photos.csv` and `summary.json` in a new `<run>/reports/segcheck_<date>/`.

## Spec conflicts and deviations

1. **New modules:** `parity_segmentation` and `mask_compare` (the spec offered `segmentation.py` or `parity_segmentation.py` for the comparison; it was split in two to stay under the 300-line guide), `funnel`, `explore`, `probe_labels`, `viz_plots` (they keep the notebooks thin, and `viz.py` under 300 lines).
2. **The scratch run is a config override in the library** (`paths.run_prefix`, `check_config`), not a new YAML under `configs/`: a copied YAML could drift from the active SAM settings, and the override always uses them.
3. **`reports.new_report_folder`:** the two existing report writers were changed to use it (same folder names, tests unchanged).
4. **`setup(update=False)`:** an extra parameter, so that the bootstrap cell does not run the git steps twice.
5. **Extras beyond the spec:** the stale-session guard, the PCA cap, the UMAP notice filter, the RuntimeError on a CPU runtime in 01, `report_lines`, `probe_report_lines`. The `env_cleanup` test fixture used to leave `CORALID_DATA_ROOT` set after a test; it now restores "absent".
6. **02 uses the legacy HDBSCAN settings (500 / 50)** for 16,080 crops (the legacy run had 44,211 masks), so it may find few clusters; both are settings at the top of the config cell. K-Means keeps the legacy 50 clusters.
7. **03 and 04 are patched, not regenerated:** only the setup cell, the intro wording and, in 04, the gated export and the scoring cell's `None` handling changed. `jobs.evaluate_baseline` was not used in 03: its report cells print tables the user relies on.
8. **Runtimes are estimates** (not measured) except the baseline's 25 minutes; the notebooks say so.
9. **Plan §3.6 says each notebook starts with `coralid.colab.setup()`;** the first cell is `BOOTSTRAP_CELL`, which calls it (the package cannot be imported before the clone exists; decided in C1).

## Found during refactor (not fixed)

- **The first dry run found a bug that real data would not have:** PCA with 50 components fails on features with fewer than 50 dimensions (fixed, see above). Real DINO features are 384-d and 1,024-d.
- **The segmentation check's per-photo table shows floats and NaN** for a photo that could not be segmented (cosmetic).
- **`data_50` is unverified:** the check assumes its photos are the same files, with the same names, as in `data_all`. If it finds none with a saved JSON it says so and suggests `data_all`; if the files differ in size it reports `frame differs`.
- **Whether CoralSCOP's generator can raise instead of returning `[]` for a photo with no masks** is still unknown (see the C1 notes); the check reports such a photo as "not segmented".
- **The real `third_party/CoralSCOP` loader has no `map_location`** (see C1): the check needs a GPU runtime, which is why 01 stops on a CPU.
- **Colab package versions:** `umap-learn` and `hdbscan` come with the `cluster` extra; nobody has installed them in Colab yet. A numpy or pandas replacement by pip would trigger the restart message.
